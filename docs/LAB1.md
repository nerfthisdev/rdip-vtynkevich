# ЛР1 — Code smells и базовый рефакторинг

## Обнаруженные проблемы

- `OrderService.createOrder` совмещал валидацию, загрузку товаров, расчёт цены,
  запись в БД и имитацию отправки письма.
- Параллельные списки товаров и расчётных позиций связывались по индексу:
  корректность сохранения зависела от совпадения их порядка и размера.
- Проверки обязательных строк дублировались, правила скидок содержали
  неименованные пороги и коэффициенты, калькулятор создавался внутри сервиса.
- Уведомление выводилось через `System.out`, минуя журнал приложения.

## Изменения

`OrderService` координирует создание заказа в одной транзакции и получает
зависимости через конструктор:

| Компонент | Ответственность |
| --- | --- |
| `OrderRequestValidator` | Обязательные данные клиента и наличие позиций |
| `OrderItemResolver` | Поиск товаров и проверка количества |
| `PreparedOrderItem` | Совместное хранение товара и проверенного количества |
| `PricingCalculator` | Расчёт стоимости и применение скидок |
| `OrderPersistence` | Сохранение заказа и отдельных позиций |
| `OrderConfirmationNotifier` | Имитация письма через SLF4J |

В калькуляторе выделены расчёт позиции, скидка клиента и купон; параметры правил
получили имена. Сохранён порядок: скидка за количество → скидка клиента → купон →
ограничение снизу нулём → скидка на крупный заказ → округление `HALF_UP`.
Пороговые сравнения остаются строгими: количество `> 10`, сумма `> 1000`.

Сохранены сообщения и порядок ошибок, количество по умолчанию `1`, тип клиента
по умолчанию `regular`, статус `new`, отдельные позиции для повторных товаров.
Все позиции проверяются и цена рассчитывается до первой записи; уведомление
вызывается после сохранения заказа и всех позиций в прежней транзакции.

## Проверка

Для проверки только ЛР1 без намеренно красных гейтов следующих работ:

```bash
mvn -B -Dtest=OrderServiceTest,OrderApiReferenceTest,PricingCalculatorReferenceTest \
  -Dmaven.test.failure.ignore=false verify
```

`OrderServiceTest` проверяет сохранение повторных позиций и количества по
умолчанию, отсутствие записи при ошибке поздней позиции, приоритет ошибок и
отправку уведомления только после успешного сохранения всех позиций.

Результат чистой сборки на Java 21: **8 тестов, 0 ошибок и падений**;
Checkstyle — **0 замечаний**, PMD — **8 замечаний** по фактическому XML-отчёту
(в неизменённых классах приложения). Сумма **8 ≤ 15** соответствует порогу ЛР1.

Полный учебный пайплайн запускается через `mvn -B verify`, после него
`python3 scripts/write_score.py` формирует баллы. Для ЛР1 нужны оба отчёта стиля,
сумма замечаний не больше 15 и успешные эталонные тесты поведения. Настройки
проверок, эталонные тесты и начальная миграция не изменялись. Нормализация БД,
характеризационные тесты калькулятора и задачи ЛР3–ЛР5 остаются следующим этапам.
